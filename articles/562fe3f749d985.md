こんにちは 👋

React Router v7.15.1 で `useRouterState` という新しい Hook が追加されました。

https://reactrouter.com/api/hooks/useRouterState

公式ドキュメントによると `useRouterState()` で取得できる値は以下のようです。

```tsx
import { unstable_useRouterState as useRouterState } from 'react-router';

const { active, pending } = useRouterState();

// Active is always populated with the current location
active.location; // replaces `useLocation()`
active.searchParams; // replaces `useSearchParams()[0]`
active.params; // replaces `useParams()`
active.matches; // replaces `useMatches()`
active.type; // replaces `useNavigationType()`

// Pending is only populated during a navigation
pending.location; // replaces `useNavigation().location`
pending.searchParams; // equivalent to `new URLSearchParams(useNavigation().search)`
pending.params; // Not directly accessible today
pending.matches; // Not directly accessible today
pending.type; // Not directly accessible today
pending.state; // replaces `useNavigation().state`
pending.formMethod; // replaces useNavigation().formMethod
pending.formAction; // replaces useNavigation().formAction
pending.formEncType; // replaces useNavigation().formEncType
pending.formData; // replaces useNavigation().formData
pending.json; // replaces useNavigation().json
pending.text; // replaces useNavigation().text
```

簡単にまとめると、ほとんどの機能は既存の Hook を置き換えたもので、`pending` で取得できる `params`、`matches`、`type` については今回の `useRouterState` で追加されたものということになります。

というわけで、今回は新しく追加された `params`、`matches`、`type` の活かしどころを考えてみたいと思います！

:::message
`useRouterState` は React Router v8.4.0 時点でも `unstable_` プレフィックスが付いた実験的な API です。patch リリースでも予告なく変更・廃止される可能性があるので、実際に使う場合は公式ドキュメントで最新の情報を確認してから使うことを推奨します🙏
:::

# 前提知識

今回は `useRouterState()` が返す `pending` で受け取れる値をもとにごにょごにょさせていくわけですが、それをするうえで React Router の Data Mode を理解しておく必要があるので、簡単に説明したいと思います！

まず、React Router には以下の 3 つのモードがあります

| モード名         | 特徴                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Declarative Mode | React RouterのRouter機能だけを使うイメージ。Router機能しか使わないので、データフェッチにはloaderじゃなくてSWRとかを使ったりする |
| Framework Mode   | loader使ったり、SSRしたり等NextやNuxtみたいにフレームワークとして使う                                                             |
| Data Mode        | Router機能に加えて、遷移先のデータ取得や更新、ローディング状態までReact Routerで管理する                                        |

なんか Data Mode だけイメージしにくいのでもう少し深掘りすると、例えば一般的な SPA だとデータ取得が必要な画面を開いたときの挙動は

```
ユーザーがリンクをクリックする
  ↓
Router が遷移先の Route を特定する
  ↓
遷移先の Component を render する
  ↓
Component 側で必要なデータの取得を開始する
（SWR / TanStack Query / useEffect など）
  ↓
データ取得が完了する
  ↓
取得したデータを使って Component を re-render する
```

のような感じになりますが、Data Mode を使うと

```
ユーザーがリンクをクリックする
  ↓
Router が遷移先の Route を特定する
  ↓
遷移先の Route に定義された loader を実行する
  ↓
必要なデータの取得が完了する
  ↓
画面遷移を commit する
  ↓
取得したデータを使って遷移先の Component を render する
```

となります。

一般的な SPA では、遷移先の画面を先に表示して、その Component 側で必要なデータを取得する構成がよくあると思います。

一方、Data Mode では、遷移先の Route に定義した loader を画面遷移の途中で実行できます。loader で待つようにしたデータについては、その取得が終わるまで遷移先の画面への切り替えを待ち、取得後に画面遷移を完了します。

つまり、「画面を表示してからデータを取りにいく」だけでなく、「必要なデータを取ってから画面を切り替える」という選択肢を Router 側で持てるのが Data Mode の特徴かなと思います。

これは実際の画面を見ると分かりやすくて、以下のサンプルのアドレスバーとデータ取得処理の関係に注目してみると、データ取得が完了してからアドレスバーの URL が切り替わっていることが確認できると思います。

![Data Modeの実演gif](/images/562fe3f749d985/dataMode.gif)

一般的な SPA では「画面を表示してからデータを取得する」のに対して、Data Mode を使うと「データを取得してから画面遷移を完了する」ようになるのが大きな違いかと思います。

また、この仕組みによって React Router は、「現在どの画面を表示しているか」だけでなく、「今どの画面へ遷移しようとしているか」という状態も把握できるということになります！

# activeとpendingってなんなの？

Data Mode のインプットが終わったので、次に `useRouterState()` が返す `active` と `pending` について説明したいと思います！

簡単に言えば

| プロパティ | 入っている値                                      |
| ---------- | ------------------------------------------- |
| active   | 現在表示中の Route に関するルーティング状態 |
| pending  | 遷移先の Route に関するルーティング状態     |

こんな関係になっています。

Data Mode では画面遷移が完了する前から「次にどの Route へ遷移しようとしているのか」を React Router が把握しているため、その情報を pending 経由で参照できます。

# 今回増えたparams、matches、typeで何がわかるの？

というわけで、今回新たに直接取得できるようになった 3 つを整理すると、以下のようになります。

| プロパティ | 取得できる値            |
| ---------- | ----------------------- |
| params     | 遷移先Routeのパラメータ |
| matches    | 遷移先でmatchするRoute  |
| type       | 遷移先へのHistory操作   |

まぁ、こんな感じに説明されてもよくわからないと思うので、実際の活用例と一緒に具体的に紹介していきたいと思います！

# pending.params の活用例

唐突ですが、前提知識のセクションで紹介した GIF を見て「なんかクリックしてからデータ取得完了までユーザーにフィードバックがないから UX 的にイマイチでは？」と思ったかもしれません。

これは確かにそうで、一応、既存の `useNavigation()` が返す `state` や `location` を使うことで遷移元の画面で Spinner を出したりできるので、UX 的にはそこまで致命的なことにはならないのですが、UI 自体は遷移先のものを先に出して、データ取得後でないと表示できない部分についてはスケルトンにするみたいな今っぽい UX にしたいと思うこともあると思います。

そこで、`pending.params` を使うことでその問題を解決したいと思います！
まずはサンプルを見てみましょう！

![pending.paramsの活用例のgif](/images/562fe3f749d985/params.gif)

画面としては社員一覧のサイドバーがあって、サイドバーの社員名をクリックすることで社員の詳細データの取得が始まり、取得が完了したら詳細データが表示されるようになっています。

社員名をクリックしたときの画面の挙動を見てみると、社員名をクリックした瞬間にサイドバーの選択状態が変わり、カード UI にクリックした社員名が先に表示されて、詳細データ表示部分にはデータ取得完了までスケルトンが表示されています。

社員名をクリックすると URL に選択中の社員に対応する userId が埋め込まれます。そして、`useRouterState()` の戻り値は画面遷移中と画面遷移後でそれぞれ以下のようになります。（説明に重要な値だけをピックアップしています）

```jsonc
// 画面遷移中（/users/1 -> /users/2 に遷移）
{
  "active": {
    "params": {
      "userId": "1",
    },
  },
  "pending": {
    "params": {
      "userId": "2",
    },
    "state": "loading",
  },
}
```

```jsonc
// 画面遷移後（/users/2 に遷移完了）
{
  "active": {
    "params": {
      "userId": "2",
    },
  },
  "pending": null,
}
```

次に、実装コードベースでやっていることを簡単に説明すると、

```tsx
const { active, pending } = useRouterState();

// 遷移先の userId。遷移していなければ undefined
const pendingUserId = pending?.params.userId;

// 一覧で取得済みの名前だけは、詳細の loader を待たずに出せる
const previewName = pendingUserId ? summaries.find((s) => s.id === pendingUserId)?.name : undefined;

// 選択のハイライトも pending を優先する
const selectedUserId = pendingUserId ?? active.params.userId;
```

params から取得できる `userId`（URL パスの動的セグメントに対応する値）を元に、すでに取得済みの社員一覧のデータと突合させてサイドバーの選択状態とカード UI に表示する社員名を画面遷移前に解決して、UI に反映させています。

ちなみに、今回の挙動を `useRouterState` なしで実現しようとした場合は既存の `useNavigation` を使うことになると思うのですが実装がかなり面倒になってしまいます。

`useNavigation().location.pathname` には遷移先の URL が入っているので、`matchPath` を使って自分でパースすれば `userId` 相当の値は取り出せます。ただ、`matchPath` に渡すパターンは `routes.ts` に書いたパスと同じ文字列をもう一度書くことになります。ルートのパスを変えたときにここを直し忘れると、型検査でもエラーにならないまま `userId` が `undefined` になり、知らないうちにバグを生んでしまうことに繋がります。

パースを避けるなら、クリックハンドラで押された id をローカル state に持っておく手もあります。ただ、これは FE の実装で陥りがちな URL の状態を別の state でも管理するという二重管理状態になるのでなるべく避けたいです。

`pending.params` はこの「遷移先のパラメータ」を React Router が解決済みの形で返してくれるので、既存の問題点を解決しながら快適な UX を提供できます！

# pending.matches の活用例

`pending.params` では、遷移先の userId を使ってサイドバーの選択とカードの社員名部分を先に表示しました。ただこれは画面の一部を差し替える話で、画面が入れ子になってくると今度は「どこを表示してどこをスケルトンにするか」という別の問題が出てきます。

サイドナビがあって、その中に一覧があって、さらに詳細とタブがある、みたいな管理画面を想定した場合、タブを切り替えたら画面全体がスケルトンになるのもありですが、もう少しピンポイントでスケルトンを表示できると「どこが変わってどこが変わらないか」をユーザーに伝えられるのでより良くなるかなと思います。

というわけで、`pending.matches` を使って UI の差し替わる範囲を絞ってみたいと思います！

どちらも `matches` の配列を先頭から見比べると

- タブ遷移: index 0〜3 は同じで、index 4 の `id` が `detail/overview` から `detail/tasks` に変わっている
- プロジェクト切り替え: index 0〜2 は同じで、index 3 は `id` が同じまま `pathname` だけ `/portal/projects/1` から `/portal/projects/2` に変わっている

ということが分かると思います。この最初に食い違った `matches` 配列の index をもとに、差し替える範囲を決めることになります。

この index は Route の階層の深さと対応していて、今回の Route の構成は以下のようになっています。（左の数字は index を表します）

```
0  root
1  └─ portal/layout                            ← サイドナビ
2     ├─ portal/projects/layout                ← プロジェクト一覧
3     │  └─ portal/projects/detail/layout      ← 詳細カードとタブ
4     │     ├─ portal/projects/detail/overview
4     │     └─ portal/projects/detail/tasks
2     ├─ portal/reports
2     └─ portal/settings
```

各レイアウトが `<Outlet />` を持っていて、3 つの遷移では入れ替わる `<Outlet />` がそれぞれ違います。

| 操作                    | Outletが入れ替わるレイアウト | そのまま残る部分                           | スケルトンになる部分 |
| ----------------------- | ---------------------------- | ------------------------------------------ | -------------------- |
| 概要 ↔ タスク           | detail/layout                | サイドナビ、一覧、カードの枠、見出し、タブ | タブの中身だけ       |
| プロジェクト1 → 2       | projects/layout              | サイドナビ、一覧                           | 詳細カード全体       |
| プロジェクト → レポート | portal/layout                | サイドナビ                                 | 一覧を含む本文全体   |

注目してほしいのは、どのレイアウトの `<Outlet />` が入れ替わるかがクリック対象によって変わっているところです。つまり、スケルトンをピンポイントに絞って表示するために各レイアウトは「今回の遷移で自分の Outlet が入れ替わるのか」を自分で判断する必要がある、ということになります。

この判定は `pending.params` だけだとできません。3 つとも遷移先のパラメータ自体は取れるのですが、「どの階層から下が差し替わるのか」という情報がパラメータからは出てこないからです。もしやるとしたら、URL の文字列を比べて `/` の数を数えるという地獄みたいな実装をすることになります。

というわけで、ここで `pending.matches` の出番です！

`active.matches` と `pending.matches` を先頭から比べて、最初に食い違った index を返す関数を作ります。この index が「今回の遷移で差し替わる階層の先頭」になります。

```tsx
const usePendingBoundary = () => {
  const { active, pending } = useRouterState();
  // 遷移していない間はpendingがnullなので、比べる相手がいない
  if (!pending) return null;

  // 遷移の前後で階層の深さが変わることがあるので、短いほうに合わせる
  // 例: /portal/reports（3階層）から /portal/projects/1（5階層）へ移る場合
  const length = Math.min(active.matches.length, pending.matches.length);

  for (let i = 0; i < length; i++) {
    const a = active.matches[i];
    const p = pending.matches[i];

    // idが違う → その階層が別のRouteに入れ替わる（reports → projects）
    // pathnameが違う → Routeは同じままパラメータだけ変わる（projects/1 → projects/2）
    if (a?.id !== p?.id || a?.pathname !== p?.pathname) {
      // 先頭から見て最初に食い違ったこの階層から下が、今回差し替わる範囲
      return i;
    }
  }

  // 共通部分は同じだが、片方だけ階層が深い（例: 一覧から詳細へ入る遷移）
  if (active.matches.length !== pending.matches.length) {
    return length;
  }

  // 完全に同じ（同じURLを開き直したときなど）
  return null;
};
```

あとは各レイアウトがこの関数が返した index（`boundary`）と、自分の階層の index（`myIndex`）を比べるだけです。

```tsx
// 境界が自分のちょうど1つ下なら、自分のOutletがスケルトンになる
const isOutletPending = boundary === myIndex + 1;

return isOutletPending ? <Skeleton /> : <Outlet />;
```

レイアウトごとに独立して判定しているので、「今回はどこを残すか」を上位のコンポーネントで集中管理する必要がありません。

## idだけでなくpathnameも比べる

`usePendingBoundary` で `id` と `pathname` の両方を比べているのには理由があります。

プロジェクト 1 から 2 への遷移で考えてみると、変わるのは `projectId` だけなので、マッチする Route は 5 つとも同じです。つまり `id` だけを比べると差分が 1 つも見つかりません。

| index | Route ID                        | active.pathname        | pending.pathname       |
| ----- | ------------------------------- | ---------------------- | ---------------------- |
| 0     | root                            | /                      | /                      |
| 1     | portal/layout                   | /portal                | /portal                |
| 2     | portal/projects/layout          | /portal/projects       | /portal/projects       |
| 3     | portal/projects/detail/layout   | /portal/projects/**1** | /portal/projects/**2** |
| 4     | portal/projects/detail/overview | /portal/projects/1/    | /portal/projects/2/    |

`matches` の各要素は Router が階層ごとに計算した `pathname` を持っているので、そちらを見れば index 3 で食い違いが見つかります。ここを `id` の比較だけで済ませると、プロジェクトを切り替えたときだけスケルトンが出なくなります。

## handleで遷移先の見た目を先に決める

`matches` から取れるのは Route の ID と pathname だけではありません。各要素は、その Route モジュールが export した `handle` を持っています。

```tsx
// app/routes/portal/projects/detail/layout.tsx
export const handle = {
  title: 'プロジェクト詳細', // ヘッダのページタイトル
  breadcrumb: '詳細', // パンくずのラベル
  contentWidth: 'full', // 本文カラムの最大幅
  skeleton: 'card', // 差し替わるときに描くスケルトンの形
} satisfies RouteHandle;
```

`RouteHandle` は React Router が用意しているものではなく、自分で定義した型です。`handle` に何を入れるかは自由なので、実装者側で決めることになります。

```jsonc
      {
        "id": "routes/portal/layout",
        "pathname": "/portal",
        "handle": {
          "title": "社内ポータル",
          "breadcrumb": "社内ポータル",
          "contentWidth": "full",
        },
      },
      {
        "id": "routes/portal/projects/layout",
        "pathname": "/portal/projects",
        "handle": {
          "title": "プロジェクト",
          "breadcrumb": "プロジェクト",
          "contentWidth": "full",
          "skeleton": "split",
        },
      },
      {
        "id": "routes/portal/projects/detail/layout",
        "pathname": "/portal/projects/1",
        "handle": {
          "title": "プロジェクト詳細",
          "breadcrumb": "詳細",
          "contentWidth": "full",
          "skeleton": "card",
        },
      },
      {
        "id": "routes/portal/projects/detail/tasks",
        "pathname": "/portal/projects/1/tasks",
        "handle": {
          "title": "タスク",
          "breadcrumb": "タスク",
          "contentWidth": "full",
          "skeleton": "table",
        },
      },

  },

```

`root` だけ `handle` を export していないので `handle` のキー自体がありません。それ以外の 4 つには、それぞれの Route が export した値がそのまま入っています。

注目したいのは末尾です。`active` は `概要`（`skeleton` は `list`）で、`pending` は `タスク`（`skeleton` は `table`）になっています。つまり遷移が確定する前から、行き先のページタイトルもスケルトンの形も分かっているということです。

あとはこれを読むだけなのですが、4 つの Route がそれぞれ `title` を持っているので、どれを採用するかを決める必要があります。

```tsx
// pending中は行き先のhandleを、そうでなければ現在のhandleを見る
const matches = pending?.matches ?? active.matches;

// handleの型はunknownなので、型ガードで絞り込んでから読む
const handles = matches.map((m) => m.handle).filter(isRouteHandle);

// 子のRouteが値を持っていれば親より優先したいので、末尾から探す
const title = handles.findLast((h) => h.title !== undefined)?.title;
```

GIF でヘッダのタイトルとパンくずがクリック直後に切り替わっているのは、これをやっているからです。スケルトンの形（カードなのか表なのかリストなのか）も同じ仕組みで決めています。

この挙動を `useRouterState` なしで実現しようとすると、けっこう厳しいです。`useNavigation().location` には遷移先の URL が入っていますが、そこからマッチする Route の階層を辿る方法も、各 Route の `handle` を読む方法もありません。`useMatches()` は配列を返してくれますが、中身は `active` の分だけです。

`pending.matches` は、遷移先の Route の階層と、各 Route が持つ `handle` をまとめて返してくれます。おかげで「どこを差し替えるか」と「差し替えた先がどんな見た目か」の両方を、遷移が確定する前に決められます！

:::message
`handle` は Route モジュールの export なので、Framework Mode のようにモジュールが分割されている構成では、行き先のモジュールがまだ読み込まれていない間は `undefined` になります。ページを開いた直後の 1 回目の遷移がこれに当たって、タイトルもパンくずも切り替わってくれません。`Link` に `prefetch="intent"` を付けてホバーの時点でモジュールを先読みさせると解消します。
:::

# pending.type の活用例

最後は `pending.type` です。ただ先に書いておくと、この値は `params` や `matches` ほど明確な使いどころが思いつきませんでした。`active.type` は既存の `useNavigationType` の置き換えでもともと取得できていた値で、`active` に対して `pending` でも値を対称的に扱えるように追加したのかなという印象です。

とはいえ、そんなまとめで終わってしまうのはなんか味気ないので、`pending.type` についての説明と、「`type` 単体では活用できないけど、他のものと組み合わせるとこんな活用ができるかも？」というケースについて書きたいと思います。

## PUSH / REPLACE / POP とは

まず、`type` が返すのは、その遷移が履歴スタックをどう操作するかです。

| 値        | 履歴スタックへの操作                             | 対応する API             |
| --------- | ------------------------------------------------ | ------------------------ |
| `PUSH`    | 新しいエントリを積む。以降のエントリは捨てられる | `history.pushState()`    |
| `REPLACE` | 今いるエントリを置き換える                       | `history.replaceState()` |
| `POP`     | スタック内の別の index へ移動する                | `popstate` イベント      |

ポイントは `POP` で、ブラウザバック・フォワードでも同じ `POP` になります。履歴スタックの index が変わったことだけを表していて、どちらへ動いたかは含みません。[React Routerの型定義](https://github.com/remix-run/react-router/blob/react-router%408.4.0/packages/react-router/lib/router/history.ts#L11-L18)にも

> A POP indicates a change to an arbitrary index in the history stack, such
> as a back or forward navigation. It does not describe the direction of the
> navigation, only that the current index changed.

と明記されています。

## typeとparamsでアニメーションを出し分ける

![pending.typeの活用例のgif](/images/562fe3f749d985/type.gif)

申し込みフォームのような、複数のステップに分かれた画面です。「次へ」で進み、「戻る」で 1 つ前に戻り、「最初からやり直す」で 1 ステップ目に戻ります。進むときは右から、戻るときは左からスケルトンがスライドし、やり直しのときはフェードします。

| 操作                         | type      | アニメーション |
| ---------------------------- | --------- | -------------- |
| 次へ                         | `PUSH`    | 右からスライド |
| 戻る（ブラウザバックも同じ） | `POP`     | 左からスライド |
| 最初からやり直す             | `REPLACE` | フェード       |

実装はこうなっています。

```tsx
const step = Number(active.params.step ?? 1);

let animClass = 'anim-fade';

// REPLACEは前後の移動ではないのでフェードのまま
if (pending && pending.type !== 'REPLACE') {
  // 戻るも進むもPOPなので、向きはステップ番号の増減で決める
  const targetStep = Number(pending.params.step ?? 1);
  animClass = targetStep < step ? 'anim-back' : 'anim-forward';
}
```

`type` と `params` で役割が分かれています。

| 判定したいこと     | 使う値                                               |
| ------------------ | ---------------------------------------------------- |
| 前後の移動かどうか | `pending.type`                                       |
| どちらへ動くのか   | `pending.params.step` と `active.params.step` の大小 |

さきほど書いたとおり `POP` は向きを持たないので、`type` だけではブラウザバックとブラウザフォワードを区別できません。そのため、実際にどちらへ動くのかは `active.params.step` と `pending.params.step` の大小で判定しています。

逆に「最初からやり直す」はステップ番号では区別できません。たとえばステップ 2 で押すと 2→1 になりますが、これは「戻る」を押したときとまったく同じ動きだからです。こちらは `REPLACE` かどうかを `pending.type` で見るしかありません。

したがって、この 2 つを組み合わせて初めて 3 通りの出し分けが可能になります。

## active.typeでは代わりにならない

「`active.type` でも同様のことができるのでは？」と思う方もいるかと思いますが、戻るを押している最中の値を見てみると、こうなっています。

```json
{
  "active": { "type": "PUSH" },
  "pending": { "type": "POP" }
}
```

`active.type` は `useNavigationType()` と同じ値で、直前に確定した遷移の種類です。いま起きているのは `POP` なのに `PUSH` が返ってきます。アニメーションを決めたいのは遷移中なので、この値を使うことはできません。

## typeで分かるのは履歴の操作だけ

`pending.type` で取得できるのは「履歴をどう操作したか」だけです。遷移中の UI で知りたいことの多くは「何が変わるか」なので、`type` の情報だけでなにかできる場面はそんなに多くないと思います。したがって、今回のように `params` と組み合わせて、はじめてやりたい判定ができるというケースが多いのかなと思います。

# まとめ

Data Mode では画面が切り替わる前から React Router が遷移先の情報を持っていて、`useRouterState()` の `pending` はそれをそのまま取得できます。おかげで「ユーザーが操作してから画面が変わるまで」の待ち時間に、遷移先に合わせた表示を出せるようになりました。

フロントエンド周りのライブラリ・フレームワークの成長のおかげで最近では UX 設計について色々な選択肢がとれるようになってきたと思います。特に UX については銀の弾丸はなく、プロダクトやユーザーの特性に合わせて試行錯誤をしていかないといけない分野だと思うので、それに対して色々な案を出せるように自分の中の引き出しも常にアップデートしていきたいですね！
